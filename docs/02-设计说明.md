# 02 设计说明

## 1. 设计目标

本系统是面向单个末端驿站的包裹管理原型，核心目标不是覆盖完整物流链路，而是保证入库、取件、取件码复用和隐私面单检索四条主链路正确、可解释、可测试。

设计遵循以下原则：

- 数据库约束兜底业务唯一性，并发下不依赖“先查再写”。
- 取件码槽位生命周期与运单生命周期彼此独立。
- 冷却状态、滞留档位等时间结果实时派生，不保存冗余结果。
- 所有时间均来自注入的 `Clock`，测试不依赖系统时钟或 `Thread.sleep`。
- Controller 只处理协议转换，事务和业务规则位于应用服务/事务服务。
- 状态变化追加事件流水，不修改历史事实。

## 2. 系统结构

```text
浏览器（HTML + CSS + JavaScript）
          │ HTTP / JSON
          ▼
Controller（参数绑定、响应封装）
          │
          ▼
Application Service（用例编排、重试）
          │
          ├── Tx Service（事务边界、状态流转）
          ├── Domain（归一化、分配、冷却策略纯函数）
          └── Repository（JPA 持久化）
                         │
                         ▼
              H2 / MySQL + Flyway
```

## 3. 核心数据模型

### 3.1 包裹 `parcel`

包裹记录保存运单、联系信息、取件码、状态、入库/出库时间和操作信息。两个可空标志承担不同唯一性职责：

- `active_flag = 1`：运单仍未完结；与 `tracking_no` 组成唯一索引。
- `code_slot_flag = 1`：取件码仍被在库件或冷却期占用；与 `pickup_code` 组成唯一索引。
- 生命周期结束后将对应标志设为 `NULL`。数据库允许唯一索引中存在多个 `NULL`，因此历史记录可以长期保留。

### 3.2 码空间 `code_space`

每一排由 `prefix` 标识，保存容量、游标、冷却天数、冷却模式和策略档位。`cursor_pos` 仅指示下次 next-fit 的搜索起点，不代表该序号必然可用。

### 3.3 事件 `parcel_event`

入库、取件、撤销、退回、催取、备注和尾号补录均追加事件。事件包含前后状态、发生时间、操作员和备注，用于审计与问题还原。

### 3.4 冷却策略日志 `cooldown_policy_log`

每次策略计算都记录指标快照、旧值、新值、档位和原因，即使没有发生调整也保留记录，保证策略可解释。

## 4. 关键业务设计

### 4.1 入库与并发控制

1. 解析并归一化联系号、取件码和取码范围。
2. AUTO 模式读取真实占用序号，使用 next-fit 从游标下一位搜索；MANUAL 模式校验完整码。
3. 在同一事务内插入包裹、追加 `INBOUND` 事件并推进游标。
4. 运单或取件码冲突由数据库唯一索引最终裁决。
5. AUTO 并发冲突时重新读取整份位图并重算；重试轮次加入搜索起点偏移，避免线程锁步碰撞。

前端的“下一码”仅是预览，不占位。最终码始终以入库响应为准。

### 4.2 next-fit 取码

`CodeAllocator` 用 `BitSet` 表示一排的真实占用情况，从游标下一位查找第一个空位，到容量上限后回绕至 1。搜索满一圈仍无空位时返回空间耗尽。无效序号会被裁剪，同一批次内新分配的序号立即写入位图，避免批内重复。

相比 first-fit，next-fit 不会持续复用最小序号，更符合站员按货架顺序放件的连续作业习惯。

### 4.3 联系号双职责

`contactNo` 用于联系，`realSuffix` 用于客户身份检索，两者不能混用：

| 类型 | 示例 | `realSuffix` 来源 |
| --- | --- | --- |
| REAL | `13812345678` | 从真实号派生 |
| MASKED | `138****5678` | 从掩码尾段派生 |
| VIRTUAL | `17012345678,8462` | 入库时可空，后续人工补录 |

解析前先做 NFKC 全半角折叠。掩码判断保留连字符，真实号/虚拟号判断再移除连字符，防止把掩码字面误识别为普通号码。

### 4.4 取件、冷却与撤销

- 取件：`PENDING → PICKED_UP`，释放运单唯一槽位，但继续持有取件码槽位进入冷却。
- 回炉：当 `outboundAt + cooldownDays <= now` 时释放取件码槽位。
- 撤销取件：仅在取件码没有被复用、同运单没有新活动记录时恢复 `PENDING`。
- 撤销入库/退回：保留原记录和流水，不做物理删除。

状态更新采用带前置状态的原子更新。受影响行数为 0 时重新读取当前状态并返回明确业务错误，不把重复操作伪装成成功。

### 4.5 自适应冷却

策略输入为容量、在库、冷却、日均入库和日均出库的指标快照：

```text
buffer = ceil(dailyInbound × bufferDays)
target = clamp(floor((capacity - inStock - buffer) / max(dailyPickup, 1)), minDays, maxDays)
```

- 可用率低于 10%：`EMERGENCY`，压缩至最短 3 天。
- 可用率低于 30%：`TIGHT`，压缩至最短 3 天。
- 正常档下调一次到位，上调每次最多 1 天。
- 目标增幅不足 `max(2, currentDays × 20%)` 时位于滞回带，维持不变。

策略本身是纯函数；读取指标、写配置、记录日志由外层服务负责。

## 5. 前端设计

前端由 Spring Boot 直接托管，无 Node/npm 构建步骤：

| 文件 | 用途 |
| --- | --- |
| `index.html` | 工作台入口与功能导航 |
| `inbound.html` | 连续入库、码预览、撤销上一件 |
| `query.html` | 分层查询、筛选、分页、取件、催取、补尾号 |
| `dashboard.html` | 今日指标、快递分布、码空间健康度 |
| `static/js/app.js` | API、错误处理、格式化、提示等共享能力 |
| `static/css/app.css` | 响应式布局与统一视觉样式 |

页面使用相对同源的 `/api/v1`，不需要 CORS。接口失败时展示业务码和后端说明；入库成功后只清除本件字段，保留操作员、快递公司和排前缀以支持连续作业。

## 6. 一致性不变量

| 编号 | 不变量 | 落地方式 |
| --- | --- | --- |
| INV-1 | 运单活动生命周期与码槽生命周期独立 | 两个 nullable flag + 两个唯一索引 |
| INV-2 | 唯一性由数据库兜底 | 事务内直接写入并翻译约束冲突 |
| INV-3 | 只保存原始事实 | 冷却、可用数、滞留档位实时计算 |
| INV-4 | 时间可测试 | 统一注入 `Clock`，测试使用 `MutableClock` |
| INV-5 | 状态更新带前置条件 | Repository 原子条件更新 |
| INV-6 | 状态变化写不可覆盖流水 | `parcel_event` 只追加 |

## 7. 测试策略

- 纯单测：归一化、next-fit、冷却策略等无副作用规则。
- MockMvc 集成测试：HTTP 状态、业务码、事务结果与流水。
- 并发测试：同排多线程入库，验证不重复和重试行为。
- 时间边界：使用 `MutableClock` 推进到冷却、滞留边界，不使用休眠。
- 测试数据库：H2 MySQL 模式，Flyway 使用与生产一致的迁移脚本。

运行全部测试：

```bash
mvn test
```

## 8. 部署与演进

默认使用 H2 文件库，适合本地演示；通过 `mysql` profile 切换 MySQL。Flyway 管理 schema，Hibernate 使用 `ddl-auto: validate` 在启动时暴露实体与数据库漂移。

后续可演进鉴权、多站点隔离、短信通知、手机号密文与盲索引、分布式定时任务互斥和运维监控，但这些能力不进入当前原型边界。

## 一、项目背景与定位

### 1.1 业务背景

末端驿站（菜鸟驿站、丰巢、快递超市等）承担快递"最后一百米"的接收、暂存、交付工作。一个典型站点的日常是：快递员上午卸下一车包裹，站员逐件扫描上架并生成取件码；白天客户陆续上门，报手机号尾号或取件码取件；晚上处理滞留件、催取、退回。

现实中的三个痛点决定了本系统的设计重心：

**其一，隐私面单让手机号不再可靠。** 面单上印的可能是掩码号 `138****5678`，也可能是 AXB 中间号 `17012345678,8462`。中间号一单一号、签收后回收复用，无法作为客户身份标识，而客户上门报的仍是真实后四位。

**其二，取件码是有限且必须循环使用的资源。** 取件码要短到能口头报出、能在货架上快速定位，因此每排的编号空间有限（默认 9999）。长期运转必然要复用旧号，但复用太快会引发取件事故——客户手机里那条"包裹在 15-1-7231"的旧通知仍然有效，家人代取时会直接拿走别人的件。

**其三，作业是连续流水式的。** 站员扫一件、放一件，中间任何一次卡顿（重码报错、要回头找空位、要手动选快递公司）都会打断节奏。系统必须服务于这个节奏，而不是让人服务于系统。

### 1.2 系统定位

单站点末端驿站包裹管理原型。功能面刻意收敛，深度投向四条主线：取件码作为可循环资源的生命周期管理、隐私面单下的手机号双职责拆分、并发与幂等的正确性、时间规则的可测试性。

### 1.3 角色

系统不做账号鉴权（原型范围外），仅通过页面上的"当前操作员"下拉框标识操作人并写入流水。实际使用者为站点员工，同时兼任入库、取件、异常处理三种角色。

### 2.2 功能明细

#### F1 包裹入库

**输入**：运单号、快递公司、联系号、收件人姓氏（可选）、取件码来源（AUTO / MANUAL）、码范围或手动码、操作员。

**处理规则**：

1. 联系号解析为 `contactType` 与 `realSuffix`（见 F14）；
2. AUTO 模式由系统在指定范围内分配取件码，MANUAL 模式校验员工输入的码是否可用；
3. 校验同一运单号不得同时存在两条未完结记录；
4. 落库为 `PENDING` 状态，记录入库时间与操作员，写 `INBOUND` 事件流水。

**输出**：包裹 ID、完整取件码、入库时间。

**异常**：运单号未完结重复入库（P2001）；取件码被在库包裹占用（P2002）；取件码处于冷却期（P2003）；该排码空间耗尽（P2004）；取件码格式非法（P1002）；联系号无法识别（P1001）。

**关键点**：运单号采用"未完结唯一"而非全局唯一。拒收重投、取错退回都会导致同一运单号二次入库，全局唯一会把这些合法场景直接拒死。

#### F2 待取件查询

**输入**：查询串 + 可选状态、滞留档位过滤 + 分页参数。

**处理规则**：前端按输入形态自动判断检索通道，优先级为取件码 → 真实后四位 → 运单号 → 完整联系号。四位纯数字走尾号等值匹配，形如 `n-n-n` 走取件码，八位以上走运单号，十一位走联系号精确匹配。

**输出**：包裹列表，每条含脱敏联系号、取件码、运单尾号、快递公司、收件人姓氏、入库时间、滞留档位与精确滞留时长。默认按滞留时长倒序，最需处理者前置。

**异常**：查无结果时返回空列表（200）而非报错，同时提示"可能是隐私单，请尝试取件码或运单号"，并在此处嵌入尾号补录入口。

**关键点**：尾号撞号在一个站点内很常见，列表必须提供足够的二次核对信息，不能只显示一个手机号尾号。

#### F3 确认取件

**输入**：包裹 ID、操作员、代取人信息（可选）。

**处理规则**：状态由 `PENDING` 原子流转至 `PICKED_UP`，记录出库时间与操作员，`active_flag` 置 NULL 释放运单唯一槽位，但 `code_slot_flag` 保持为 1 进入冷却期，写 `PICKUP` 事件流水。

**输出**：出库时间、该码预计回炉日期。

**异常**：包裹已取件（P2005，返回上次取件时间与操作人）；状态非法（P2007）。

**关键点**：重复取件不做静默幂等成功。"已被他人取走"是必须让站员立刻知道的信息，静默成功会掩盖取件事故。前端将其渲染为温和提示而非红色报错。

#### F4 滞留标识

**处理规则**：滞留由 `now − inbound_at` 在查询时实时计算，**不落库、不设定时任务**。分三档：48 小时内正常、48 至 72 小时橙色预警、超过 72 小时红色告警。同时返回精确滞留时长供前端显示"已滞留 3 天 2 小时"。

**关键点**：滞留不改变任何资源归属，落库只会引入"任务未跑到显示错误""取件后忘记回滚"两类不一致。这与 F6 回炉形成对照，判据是同一条：是否影响他人对资源的获取。

#### F5 取件码生成与循环复用

**规则**：取件码形如 `15-1-7231`，语义为"15 号货架第 1 排的 7231 号识别码"。末位不对应物理槽位，仅用于在一排范围内锁定包裹——排内范围已经足够小，识别码只需可读、不需与位置对应。

AUTO 模式支持三种范围：`ROW` 锁定到排（扫码连续入库默认）、`SHELF` 在该货架各排中挑占用率最低的一排、`FULL` 在全部启用排中选择。

分配采用 next-fit：从游标位置向后取第一个可用号，到顶回绕至 1，转满一圈无空位判定耗尽。**不采用 first-fit**，原因有二：取最小空闲号会让站员回头找位置，打断流水作业；且刚释放的号立刻被复用，复用间隔过短，取件事故风险高。next-fit 的复用距离约等于"空间上限 − 当前占用数"，天然提供了安全间隔。

**异常**：该排码空间耗尽（P2004），返回可用的替代排列表。

#### F6 冷却期与回炉

**规则**：包裹出库后，其取件码需经过冷却期才允许复用，防止旧通知导致取错件。冷却期按排配置，可自动调节或手动指定。

冷却状态**不以绝对时间戳落库**，而是在判定时由 `outbound_at + 当前冷却天数` 实时计算。回炉任务每小时批量将已过冷却期的槽位 `code_slot_flag` 置 NULL；同时分配路径在选中号后按需自愈，若该号冷却已过但 flag 未清理，在同一事务内定向释放再插入。两者构成双保险，任务延迟不阻塞入库，分配疏漏由任务兜底。

**关键点**：槽位占用量 = 在库量 + 冷却量。一排日周转 50 件、冷却 7 天则常态占用约 400 个码，占 9999 空间的 4%，空间压力可忽略——这个测算是 F7 的前提。

#### F7 冷却期自适应调节

**目标**：在保证不会没号可用的前提下，让冷却期尽可能长。

**规则**：每日凌晨按排计算目标冷却天数，公式见 §9。可用率高于 30% 为 NORMAL 档按公式计算，10% 至 30% 为 TIGHT 档压到下限并告警，低于 10% 为 EMERGENCY 档允许提前复用。缩短一次到位，延长每次最多 +1 天，并设滞回带防抖。每次决策写日志，含完整指标快照。

支持按排手动指定固定值，但手动值须过安全校验，超出安全上限时拒绝并返回建议值。

**关键点**：可解释性是这类自动机制的生命线。站员看到 15-1 是 4 天而 15-2 是 30 天，必须能查到为什么。

#### F8 扫码连续入库

**规则**：站员锁定一排与快递公司后进入连续模式，页面大字号显示"下一个取件码"，运单号输入框自动聚焦。扫描枪一扫回车即提交，成功后清空并重新聚焦，序号自动前进，已入库列表在下方倒序滚动。必须提供"撤销上一件"。

**关键点**：扫描枪本质是键盘输入加回车，无需任何对接成本。"下一个取件码"来自预览接口，**仅用于展示，不具备占位效力**，真正的分配必须在入库事务内完成。

#### F9 批量取件

**规则**：按真实后四位聚合同一客户的多件包裹，一次性出库，返回逐条成功与失败明细，部分失败不整体回滚。

**关键点**：聚合键必须是 `real_suffix` 而非 `contact_no`。虚拟号一单一号，按联系号聚合会把同一客户的三个包裹拆成三组。

#### F10 撤销取件与状态流水

**规则**：`PICKED_UP` 可撤销回 `PENDING`，重新占用码槽位、恢复 `active_flag`、清空出库时间。撤销**不覆盖历史**，而是追加一条 `CANCEL_PICKUP` 事件，流水中完整保留"曾于某时出库、某时撤销、操作人是谁"。

所有状态变更（入库、取件、撤销、退回、催取、补录尾号、槽位释放、强制复用）一律写 `parcel_event`。

**异常**：撤销时该码已被复用（P2006），提示人工改派新码。

#### F11 催取记录

**规则**：对滞留包裹执行催取，记录催取次数与最后催取时间，写流水。真实驿站超期要收费或退回，催取记录是依据。

#### F12 当日看板

**输出**：当日入库、出库、当前在库、滞留件数四个核心指标；按快递公司的分布；各排的容量、在库、冷却中、可用数、当前冷却天数与档位标记。

#### F13 测试用例

见 §12，共 22 条，提交时收敛为 10 条。

#### F14 联系方式解析与尾号补录

**规则**：联系号按形态解析为三类。真实号 `^1[3-9]\d{9}$` 直接截取后四位；掩码号 `138****5678` 从尾段提取；AXB 虚拟号允许 `real_suffix` 为空，支持后续补录。校验按类型分支——真实号严格校验，虚拟号只校验字符集与长度上限，避免把合法的带分机号误判为非法输入。

补录入口嵌在"查询无结果"处，使数据补全发生在真实作业动线中，而非单独做一个管理页面。

## 三、术语表

| 术语                | 定义                                                         |
| ------------------- | ------------------------------------------------------------ |
| 取件码 pickupCode   | `15-1-7231`，排内识别码，末位不对应物理槽位                  |
| 排前缀 codePrefix   | `15-1`，码空间划分单位，所有分配与统计的维度                 |
| 排内序号 codeSeq    | 末段整数，`1 ~ capacity`（默认 9999）                        |
| 码槽位 code slot    | 一个 `(codePrefix, codeSeq)` 组合，有 FREE / OCCUPIED / COOLING 三态 |
| 回炉 / 冷却期       | 出库后该码需经过的不可复用时间                               |
| 滞留 overdue        | 入库超 48 小时未取，派生属性，不落库                         |
| 联系号 contactNo    | 面单号码，可能是真实号、掩码号或 AXB 虚拟号                  |
| 真实尾号 realSuffix | 客户口头报出的真实手机号后四位，检索主键                     |

## 四、核心不变量（硬约束）

**INV-1｜两个生命周期相互独立。** 运单生命周期由 `active_flag` 表达（PENDING 为 1，终态 NULL），码槽位生命周期由 `code_slot_flag` 表达（占用或冷却中为 1，回炉后 NULL）。包裹取走时 `active_flag` 立即置 NULL，但 `code_slot_flag` 仍为 1 直到冷却结束。**用一个字段承担两者会直接导致冷却失效**，这是本系统最容易写错的地方。

**INV-2｜唯一性一律由数据库约束兜底，禁止"先查后插"。** 查询只用于给出友好提示，真正的防线是唯一索引抛出的 `DataIntegrityViolationException`。

**INV-3｜只落原始事实，不落策略推论。** `outbound_at` 是事实必须存；"何时可复用"是当前冷却策略的推论，**不得存为绝对时间戳并用于判定**，否则策略调整对存量数据无效，除非全表回刷。同理滞留实时计算，不落库。

**INV-4｜所有当前时间取自注入的 `Clock`。** 禁止直接调用 `LocalDateTime.now()` 或 `System.currentTimeMillis()`。这是时间规则可自动化测试的前提。

**INV-5｜状态流转使用带前置条件的原子更新。** 一律 `update ... where id = ? and status = ?`，以受影响行数判定结果。

**INV-6｜所有状态变更写 `parcel_event` 且不覆盖历史。** 撤销不是"改回去"，而是追加反向事件。

```sql
create table parcel (
    id                  bigint auto_increment primary key,
    tracking_no         varchar(32)  not null,
    courier             varchar(16)  not null,

    contact_no          varchar(24)  not null,
    contact_type        varchar(8)   not null,   -- REAL / MASKED / VIRTUAL
    real_suffix         varchar(4),              -- 可空：AXB 单入库时未知
    suffix_source       varchar(12),             -- DERIVED / MASK / PLATFORM / MANUAL
    receiver_name       varchar(32),

    code_prefix         varchar(16)  not null,
    code_seq            int          not null,

    code_reuse_forced   tinyint      default 0,  -- 1=EMERGENCY 提前复用

    status              varchar(16)  not null,   -- PENDING / PICKED_UP / RETURNED

    outbound_at         datetime(3),
```

## 八、核心业务实现

### 8.1 取件码归一化（先于校验）

扫描枪与手工录入会产生字面不同但语义等价的输入：全角减号、前后空格、`15-1-0731` 这类前导零。**不归一化，唯一索引形同虚设**——`15-1-0731` 与 `15-1-731` 会作为两行共存，但物理上是同一个码。

```java
public final class PickupCodeNormalizer {
    private static final Pattern PATTERN = Pattern.compile("^\\d{1,3}(-\\d{1,4}){1,2}$");

    public static PickupCodeVO normalize(String raw) {
        if (raw == null) throw new BizException(ErrorCode.CODE_FORMAT_INVALID, "取件码为空");
        String s = Normalizer.normalize(raw, Normalizer.Form.NFKC)   // 全角转半角
                             .replaceAll("[\\s\\u3000]", "")
                             .replace('—', '-').replace('–', '-').replace('_', '-');
        String[] seg = s.split("-");
        if (seg.length < 2 || seg.length > 3)
            throw new BizException(ErrorCode.CODE_FORMAT_INVALID, "取件码段数应为 2 或 3");
        StringBuilder sb = new StringBuilder();
        int[] nums = new int[seg.length];
        for (int i = 0; i < seg.length; i++) {
            if (!seg[i].matches("\\d{1,4}"))
                throw new BizException(ErrorCode.CODE_FORMAT_INVALID, "取件码含非法字符");
            nums[i] = Integer.parseInt(seg[i]);              // 去前导零
            if (i > 0) sb.append('-');
            sb.append(nums[i]);
        }
        String code = sb.toString();
        if (!PATTERN.matcher(code).matches())
            throw new BizException(ErrorCode.CODE_FORMAT_INVALID, "取件码格式不符");
        int last = code.lastIndexOf('-');
        return new PickupCodeVO(code, code.substring(0, last), nums[seg.length - 1]);
    }
}
```

`PickupCodeVO(fullCode, prefix, seq)` 是入库流程内部唯一允许流通的码表示，DTO 里的字符串一律先经此转换。

### 8.2 码分配：位图 + 游标 + next-fit

不写 gap-finding SQL（H2 与 MySQL 方言不通用且难调试）。一次索引覆盖扫描把该排占用号全捞出来，在内存求解。

**占用判定必须体现派生冷却（INV-3）：**

```java
public interface ParcelRepository extends JpaRepository<Parcel, Long> {

    /** 加载该排"真正不可用"的序号：在库中，或已出库但仍在冷却期内 */
    @Query("""
        select p.codeSeq from Parcel p
        where p.codePrefix = :prefix and p.codeSlotFlag = 1
          and (p.outboundAt is null or p.outboundAt > :boundary)
        """)
    List<Integer> findOccupiedSeqs(@Param("prefix") String prefix,
                                   @Param("boundary") LocalDateTime boundary);
}
```

`boundary = now − effectiveCooldownDays`。`outboundAt is null` 表示在库，一律占用；`outboundAt > boundary` 表示冷却未满。策略天数一改，全量存量记录立即生效，零回刷。

分配器是纯函数，不碰数据库、不碰时钟，回绕、满位、跳号全部可用纯单测覆盖：

```java
public final class CodeAllocator {

    /** next-fit：从游标下一位向后找第一个空位，到顶回绕至 1，转满一圈返回 empty */
    public static OptionalInt nextFit(int capacity, int cursor, Collection<Integer> occupied) {
        BitSet used = new BitSet(capacity + 1);
        occupied.forEach(s -> { if (s >= 1 && s <= capacity) used.set(s); });
        if (used.cardinality() >= capacity) return OptionalInt.empty();

        int start = (cursor % capacity) + 1;
        int seq = used.nextClearBit(start);
        if (seq > capacity) {
            seq = used.nextClearBit(1);
            if (seq > capacity) return OptionalInt.empty();
        }
        return OptionalInt.of(seq);
    }

    /** 批量入库：一次取 N 个空位，避免 N 次往返 */
    public static List<Integer> nextFitBatch(int capacity, int cursor,
                                             Collection<Integer> occupied, int n) { ... }
}
```

capacity 取 9999 时 `BitSet` 仅 1.25KB，几百个 int 的加载亚毫秒级，开销可忽略。

### 8.3 入库流程：事务内分配 + 事务外重试

**这是全系统最容易写错的一段，请严格照此结构实现。**

事务单元（内层）：

```java
@Service
@RequiredArgsConstructor
public class InboundTxService {

    private final ParcelRepository parcelRepo;
    private final CodeSpaceRepository spaceRepo;
    private final CooldownQueryService cooldownQuery;
    private final EventRecorder events;
    private final Clock clock;

    @Transactional
    public Parcel inbound(InboundCommand cmd) {
        LocalDateTime now = LocalDateTime.now(clock);
        CodeSpace space = spaceRepo.findEnabled(cmd.prefix())
                .orElseThrow(() -> new BizException(ErrorCode.NOT_FOUND, "货架排不存在或已停用"));
        int cooldownDays = cooldownQuery.effectiveDays(space);
        LocalDateTime boundary = now.minusDays(cooldownDays);

        int seq = resolveSeq(cmd, space, boundary, now);   // AUTO 走位图，MANUAL 走校验

        // 按需自愈：冷却已过但 flag 未被回炉任务清理时定向释放，避免撞唯一索引
        parcelRepo.releaseSlotIfCooled(space.getPrefix(), seq, boundary);

        Parcel p = Parcel.newInbound(cmd, space.getPrefix(), seq, now);
        parcelRepo.saveAndFlush(p);          // ← 必须 flush，把约束冲突提前到可捕获位置

        space.setCursorPos(seq);             // 游标无需加锁，见下文
        space.setUpdatedAt(now);

        events.record(p, EventType.INBOUND, null, ParcelStatus.PENDING, cmd.operator(), null);
        return p;
    }
}
```

外层重试（**不加 `@Transactional`，且必须是另一个 Bean**）：

```java
@Service
@RequiredArgsConstructor
public class InboundAppService {

    private static final int MAX_RETRY = 3;
    private final InboundTxService txService;

    public ParcelVO inbound(InboundCommand cmd) {
        for (int i = 0; i < MAX_RETRY; i++) {
            try {
                return ParcelVO.of(txService.inbound(cmd));
            } catch (DataIntegrityViolationException e) {
                if (isTrackingConflict(e))                  // 运单号冲突不重试
                    throw new BizException(ErrorCode.TRACKING_DUPLICATED, ...);
                if (cmd.codeMode() == CodeMode.MANUAL)      // 手动指定码冲突不重试
                    throw toCodeConflict(cmd);
                // AUTO：重新加载位图再取号（禁止简单地 seq+1）
            }
        }
        throw new BizException(ErrorCode.CODE_SPACE_BUSY, "货位繁忙，请重试");
    }
}
```

三个必须遵守的点：

其一，**重试循环不能写在事务方法内部**。约束冲突异常一旦冒泡出 `@Transactional` 边界，事务已被标记 rollback-only，原地重试会抛 `UnexpectedRollbackException`。同理外层必须调用另一个 Bean，自调用不走 Spring 代理，事务注解直接失效。

其二，**必须 `saveAndFlush`**。JPA 默认在事务提交前才 flush，那时异常已在 catch 之外触发。

其三，**重试时重新加载位图，不要把序号简单加一**。三个请求同时进来时盲目加一会继续撞。

游标为什么不加锁：游标的正确性不影响系统正确性，只影响复用间隔的质量。并发丢失更新最坏是少前进一格，位图会自然跳过已占用位。识别出哪些状态是"尽力而为"的、不必用强一致手段保护，是控制复杂度的关键。

### 8.7 回炉任务

回炉是真正改变资源归属的状态变更，必须落库——与"滞留不落库"形成对照，判据同为"是否影响他人对资源的获取"。

```java
@Scheduled(cron = "0 5 * * * *")                            // 每小时第 5 分钟
@SchedulerLock(name = "codeReaper", lockAtMostFor = "10m")  // 多实例互斥，可选
public void reap() {
    LocalDateTime now = LocalDateTime.now(clock);
    for (CodeSpace space : spaceRepo.findAllEnabled()) {
        int days = cooldownQuery.effectiveDays(space);
        int n = parcelRepo.bulkReleaseCooled(space.getPrefix(), now.minusDays(days));
        if (n > 0) log.info("reaped {} slots in {}", n, space.getPrefix());
    }
}
```

由于 §8.3 已实现分配时按需自愈，该任务**退化为纯优化项**（缩小位图规模），延迟不阻塞入库；反过来即使分配路径有疏漏，任务也能兜住。双保险结构，两边都不能省。

## 九、冷却期自适应调节

### 9.1 参数（已定稿）

| 参数                 | 值    | 说明                             |
| -------------------- | ----- | -------------------------------- |
| `minDays`            | **3** | 下限，TIGHT / EMERGENCY 档取此值 |
| `maxDays`            | 90    | 上限                             |
| `bufferDays`         | **3** | 预留三天入库量                   |
| `defaultDays`        | 7     | 新建排的初始值                   |
| `tightThreshold`     | 0.30  | 可用率低于此进入 TIGHT           |
| `emergencyThreshold` | 0.10  | 可用率低于此进入 EMERGENCY       |
| EWMA α               | 0.3   | 近 14 天日计数平滑系数           |

### 9.2 模型

一排的占用量 = 在库量 + 冷却量，稳态下冷却量 ≈ 日出库量 × 冷却天数。要求任何时刻可用数不低于安全水位，解出闭式解：

```
buffer          = ceil(dailyInboundRate × 3)
maxCooldownDays = (capacity − inStock − buffer) / dailyPickupRate
target          = clamp(floor(maxCooldownDays), 3, 90)
```

buffer 按"日均入库量 × 3 天"而非固定比例。固定比例对低周转货架严重过度保守——一排每天只走 5 件时，20% 的比例相当于预留了 400 天的量。

代入真实量级：capacity 9999、在库 400、日入库日出库各 50，则 `buffer = 150`，`(9999 − 400 − 150) / 50 ≈ 188 天`，经 clamp 后取 `maxDays = 90`。**说明在实际驿站规模下冷却期完全可以顶到上限，v2 里 7 天的默认值极度保守。** 这个测算本身就是结论：先算清约束边界，再决定要不要上复杂机制。

`dailyInboundRate` 与 `dailyPickupRate` 取近 14 天日计数的 EWMA，避免大促单日尖峰把冷却期一把砍到底。

### 9.3 分档与响应规则

| 档位      | 触发条件（available / capacity） | 行为                       |
| --------- | -------------------------------- | -------------------------- |
| NORMAL    | > 30%                            | 按闭式解计算，经滞回后写入 |
| TIGHT     | 10% ~ 30%                        | 强制压到 3 天，看板告警    |
| EMERGENCY | < 10%，或分子 ≤ 0，或分配失败    | 压到 3 天，且允许提前复用  |

**缩短要快、延长要慢。** 号不够用会直接阻断入库作业，是生产事故；冷却期短一点只是提高取错件概率。因此下调允许一次到位，上调每次最多 +1 天逐步爬升。

**加滞回带避免抖动。** 仅当 `target − current ≥ max(2, current × 20%)` 时才上调，否则维持不变。滞回只在 NORMAL 档生效，**不得阻塞下调**。

EMERGENCY 档的降级行为：忽略冷却，选 `outbound_at` 最早的已出库码强制复用，置 `code_reuse_forced = 1`，写 `SLOT_FORCE_REUSE` 事件，列表页显示"提前复用"标记提醒核对。**业务连续性优先于冷却保证**——宁可复用一个只冷却了两小时的码，也不能让站员卡在页面上无法入库。注意强制复用只能从 `outbound_at is not null` 的行中选，**永远不得抢占在库包裹的码**。

### 9.4 纯函数实现

```java
public record SpaceMetrics(String prefix, int capacity, int inStock, int cooling,
                           double dailyInbound, double dailyPickup) {
    public int available()         { return capacity - inStock - cooling; }
    public double availableRatio() { return capacity == 0 ? 0 : (double) available() / capacity; }
}

public record CooldownDecision(int newDays, Tier tier, boolean changed, String reason) {}

public final class CooldownPolicy {

    public static CooldownDecision decide(SpaceMetrics m, int currentDays, CooldownConfig cfg) {
        double ratio = m.availableRatio();

        if (ratio < cfg.emergencyThreshold())
            return apply(currentDays, cfg.minDays(), Tier.EMERGENCY, "可用率过低，强制最短冷却");
        if (ratio < cfg.tightThreshold())
            return apply(currentDays, cfg.minDays(), Tier.TIGHT, "可用率偏紧，压缩冷却期");

        int buffer = (int) Math.ceil(m.dailyInbound() * cfg.bufferDays());   // bufferDays = 3
        int numerator = m.capacity() - m.inStock() - buffer;
        if (numerator <= 0)
            return apply(currentDays, cfg.minDays(), Tier.EMERGENCY, "缓冲已耗尽");

        double rate = Math.max(m.dailyPickup(), 1.0);                        // 防除零
        int target = clamp((int) Math.floor(numerator / rate),
                           cfg.minDays(), cfg.maxDays());                    // [3, 90]

        if (target < currentDays)                                            // 快下调，一次到位
            return new CooldownDecision(target, Tier.NORMAL, true, "容量收紧，下调");

        int hysteresis = Math.max(2, (int) (currentDays * 0.2));             // 滞回带
        if (target - currentDays < hysteresis)
            return new CooldownDecision(currentDays, Tier.NORMAL, false, "位于滞回带内，维持");

        return new CooldownDecision(Math.min(currentDays + 1, cfg.maxDays()),
                                    Tier.NORMAL, true, "容量宽裕，慢爬升 +1 天");
    }
}
```

**策略与执行必须分离。** `decide` 不碰数据库、不碰 `Clock`，入参是指标快照、出参是决策结果，因此滞回、非对称响应、clamp、分档切换全部可用纯单测覆盖，一个用例一行断言，无需造数据也无需 Spring 上下文。副作用（读指标、写配置、记日志）留在外层 `CooldownPolicyApplier`。

### 9.5 执行时机与手动覆盖

`CooldownPolicyApplier` 每日凌晨低峰跑一次（冷却期是天级量纲，无需小时级抖动），同时在分配路径上做事件触发：某排可用率跌破 TIGHT 线时立即重算，不等次日。每次决策无论是否变更都写 `cooldown_policy_log`，含完整指标快照。

`cooldown_mode = MANUAL` 时用管理员设定的固定值，但仍须过安全校验：若会导致可用率跌破 TIGHT 线，返回 `P3001` 并给出建议上限，避免人为设一个 300 天把系统锁死。

**预览接口不具备占位效力**，仅用于前端显示"下一个是 15-1-7232"。真正的分配必须在入库事务内完成；做成"前端取号后带号提交"会把时间窗人为放大到秒级，重码不可避免。

批量接口一律采用部分成功语义，返回逐条明细，不因单条失败整体回滚。

## 十一、前端要求

主界面是连续入库页。顶部锁定排与快递公司，大字号显示"下一个取件码"，运单号输入框自动聚焦。扫描枪本质是键盘输入加回车，无需对接成本：一扫回车即提交，成功后清空并重新聚焦，序号自动前进，已入库列表在下方倒序滚动。必须提供"撤销上一件"——扫错、放错架是高频情况。

手动录入为独立切换模式，冲突时必须展示原因（占用 / 冷却）与建议码，支持一键采纳。

查询页承载分层检索、滞留分级染色（48 小时内正常、48–72 小时橙、超 72 小时红，并显示精确滞留时长）、批量取件与催取，查无结果时提供尾号补录入口。

看板页展示当日入库、出库、在库、滞留四个数字，按快递公司分布，以及各排的可用率、当前冷却天数与档位标记。

```java
void concurrentInbound_shouldNotDuplicateCode() throws Exception {
    CountDownLatch start = new CountDownLatch(1);

    List<Future<ParcelVO>> fs = IntStream.range(0, 2).mapToObj(i ->

}
```

## 十三、禁止事项（Code Review 检查表）

写完自查，以下会直接打回：直接调用 `LocalDateTime.now()`；用一个 flag 同时表达运单完结与码槽位释放；把冷却截止时间以绝对时间戳落库并用于判定；把滞留状态落库或为其写定时任务；先 `select` 查重再 `insert`；重试循环写在 `@Transactional` 方法内部；同一 Bean 内自调用事务方法；用 `save` 而非 `saveAndFlush` 导致约束冲突无法捕获；重试时把序号简单加一而不重新加载位图；强制复用时抢占在库包裹的码；批量取件按 `contact_no` 聚合；用 `like '%xxxx'` 做尾号检索；异常堆栈返回前端；事务注解出现在 Controller；`CooldownPolicy` 或 `CodeAllocator` 中出现数据库或时钟依赖。

## 十四、技术栈与交付形态

Spring Boot 3 + JDK 17 + Spring Data JPA + H2 文件模式 + Flyway + springdoc-openapi，前端 Vue 3 CDN 版单页置于 `src/main/resources/static`。目标为 `mvn spring-boot:run` 一条命令启动、浏览器直达，不依赖 MySQL 安装与 npm 构建，同时保留 `application-mysql.yml` profile 说明生产可平滑切换。

种子数据必须刻意构造：真实号、掩码号、AXB 号三类样本；跨越 48 与 72 小时边界的存量包裹；处于冷却期与冷却刚过期的历史码；某一排接近容量上限。目的是让评审者打开页面即可看到异构输入处理、滞留分级与码回收的实际效果，不必自己造数据。
